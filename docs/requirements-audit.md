**결론:** 현재 기록만으로 전체 요구 충족을 선언할 수 없다. 우선순위는 sudo 그룹의 실제 권한 검증, monitoring 지표의 의미·최신 설치본 대조, 평가용 변경 시연과 최종 제출 디스크 확인이다. 반면 고유 사용자 수·used/total 비율·게스트 소켓 수·단일 LUKS 안 여러 LV는 근거 없이 오류로 단정하거나 다른 구현으로 바꾸지 않는다.

## monitoring 지표를 실제로 무엇으로 세는가

근거는 과제 p.10, [현재 전체 코드](cheatsheet.md#34-전체-출력을-wall-한-번으로-전달), 학습 기록의 10월 14일 부분 구현·원자료·방송 확인 절이다. 아래 검증은 제안이며 새 실행 결과가 아니다.

| 항목 | 현재 측정량·판정 | 확인할 최소 비교 |
|---|---|---|
| OS·커널 | `uname -a`의 게스트 OS 아키텍처·커널. 요구에 맞는 해석. 배포판 릴리스 자체는 별도 `/etc/os-release` | 표시값을 원자료와 대조. 배포판 버전을 uname만으로 증명하지 않음 |
| physical / vCPU | 고유 온라인 소켓 ID / 온라인 논리 CPU 행 수. 실제 1/2 표본 확인. VM에서 보이는 토폴로지라는 합리적 해석 | `lscpu`와 대조. 호스트의 실제 물리 소켓 수라고 설명하지 않음. 오프라인 CPU가 있으면 전체/온라인 차이 구분 |

| CPU load | vmstat 두 번째 표본의 100−id. 직전 약 1초의 비유휴 비율이며 load average가 아님. I/O wait·steal도 포함 | 마지막 행의 id와 대조. 순수 계산 시간이라고 설명하지 않음 |

| Connections | ESTABLISHED TCP 소켓 행 수. 원문은 active connections, 예시는 TCP ESTABLISHED이므로 합리적 해석 | 새 SSH 연결 전후 `ss`와 비교. 모든 프로토콜 연결 총수라고 주장하지 않음 |
| User log | who에서 고유 로그인명을 세므로 같은 계정 두 세션은 1. 원문은 users이며 sessions를 명시하지 않음 | **확정 오류 아님.** 같은 계정 중복 접속과 다른 새 계정 접속을 구분. 세션 수로 바꾸려면 근거가 필요하며 `who | wc -l`로 무조건 교체하지 않음 |
| Network | enp0s3의 IPv4 한 개·MAC. 현재 구성에는 근거 있음 | NIC 변경·복수 IPv4가 있을 때의 일반성을 주장하지 않고 현재 `ip` 출력과 대조 |
| Sudo | `sudoreplay -d /var/log/sudo -l` 목록의 보관 I/O 세션 수. 전체 sudo 실행 명령 수와 동일성 미검증 | 이미 확보한 관리자 셸에서 sudo를 추가로 쓰지 않고 전후 목록을 읽고, 새 사용자에게 비밀 없는 sudo 명령 한 번을 실행시켜 +1 및 사용자·명령·TSID 대응 확인. 조회 자체의 sudo 실행이 수치를 늘리지 않게 구분 |

Sudo 집계는 실행마다 한 개의 I/O 세션이 생기고 모두 보관된 범위에서는 명령 실행 횟수의 근거가 될 수 있다. 로깅 도입 전 실행·삭제된 세션·로깅 예외는 복원하지 못한다. sudo로 연 셸 내부의 모든 하위 명령을 별도 sudo 실행으로 세는 것도 아니다. 과제는 “시스템 수명 전체”라는 기간을 지정하지 않는다. 따라서 무조건 영구 누적 시스템을 새로 만들 필요는 없지만, 현재 보관 목록과 요구한 실행 횟수의 범위가 같다는 설명·검증은 필요하다. journal 전체 행 수로 바꾸면 서비스 메시지·회전·중복 등 다른 오류가 생기므로 대안이 자동으로 더 정확하지 않다.

원문은 오류가 표시되지 않아야 한다고 요구한다. 현재 단순 코드는 vmstat 입력이 비면 100%, 수집 명령 실패 뒤 wc가 0을 만들 수 있다. 고정 표본 시험으로 이 한계는 재현되지만 사용자 VM에서 해당 실패가 발생했다는 증거는 아니다. 정상 실행 출력의 성공도 모든 실패 상황의 처리를 증명하지 않는다. 이번 감사는 승인된 단순 코드에 방어 옵션·함수를 일괄 추가하지 않았다.

도구 근거: [libpwquality 공식 설정 설명](https://raw.githubusercontent.com/libpwquality/libpwquality/master/doc/man/pwquality.conf.5.pod)의 usercheck·credit·enforce_for_root, [공식 구현](https://raw.githubusercontent.com/libpwquality/libpwquality/master/src/check.c)의 distance·similar·wordcheck. upstream을 읽은 결과이며 VM 설치 버전의 모든 동작을 직접 시험한 결과가 아니다. 삭제·치환 거리 계산만 보고 특정 암호가 전체 품질 검사를 통과한다고 단정하지 않는다.

## 이번 교정과 다음 실행 순서

이번에는 모호한 지표를 다른 해석으로 몰래 바꾸지 않고, 사용자명 검사 예외와 비밀번호 차이 계산의 설명을 보완했다. 현재 코드 사본·과거 학습 기록·실제 VM 상태는 보존했다. 감사의 미검증을 학습 로그의 실패나 완료로 기록하지 않는다.

1. 현재 설치본과 sudo 정책을 읽어 문서 버전과 실제 상태를 구분한다.
2. sudo 그룹 정책을 실제 적용하기로 한 시점에 새 사용자 실행·로그를 검증한다. wheel 제거는 이번 감사의 실행 항목이 아니다.
3. 가용량 표시와 sudo 집계 범위를 정하고, 필요한 최소 변경만 검증한다. users·CPU·df 비율은 정의를 설명하며 원자료와 비교한다.
4. 평가 진행본의 hostname 재부팅·8080·매분/중단 재부팅·여러 터미널 수신을 확인하고 원복한다.
5. 실제 최종 구성을 제출 README에 맞춘 뒤 종료·백업·해시·signature·제출 루트를 대조한다.

이 순서는 향후 사용자 실습을 위한 제안이다. 본 감사는 설정 변경·새 계정 생성·암호 시험·로그 삭제·VM 부팅·디스크 복사·학교 저장소 제출을 수행하지 않았다.
