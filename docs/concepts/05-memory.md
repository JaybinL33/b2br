# 하드웨어 자원과 메모리

[개념 지도](../concepts.md) · 먼저 읽기: [운영체제](01-os.md), [프로세스](03-process.md)

## 계산하는 장치와 정보를 담는 단위

**비트(bit)**는 두 상태를 표현하는 정보 단위이며 **바이트(byte)**는 보통 8비트다. 저장 용량의 GB는 10억 바이트, GiB는 2의 30제곱 바이트다. 표시 이름과 계산 기준이 다르면 같은 디스크도 숫자가 다르게 보인다. 현재 monitoring은 `free -m`·`df -m`의 기준에 맞춰 사용량과 전체 용량을 모두 MiB로 표기한다. 과제 원문 예시의 MB·Gb 표기와는 구분한다.

**CPU**는 명령을 실행하는 장치다. CPU 안의 **코어(core)**는 독립적으로 명령을 진행할 수 있는 실행 자원이고, **SMT**는 한 코어의 일부 자원을 공유하면서 여러 하드웨어 실행 흐름을 제공하는 기술이다. 운영체제가 보는 논리 CPU 수가 물리 코어 수보다 많을 수 있는 이유다. 프로세스의 소프트웨어 스레드와 CPU의 하드웨어 스레드는 이름이 비슷해도 서로 다른 층이다.

**명령어 집합(ISA)**은 CPU가 이해하는 명령과 레지스터 등의 약속이다. **x86-64**와 **AArch64**는 서로 다른 명령어 집합의 예다. 같은 Linux 프로그램 소스라도 대상 ISA에 맞게 컴파일해야 실행 파일의 명령을 CPU가 이해한다. 소프트웨어가 사용하는 데이터 형식·호출 규칙까지 맞추는 ABI는 ISA와 연결되지만 같은 개념은 아니다.

**RAM**은 실행 중인 프로그램과 데이터를 빠르게 보관하는 주기억장치다. 일반적인 RAM 내용은 전원이 꺼지면 유지되지 않는다. SSD나 HDD는 전원 이후에도 데이터를 보관하는 저장장치지만 RAM보다 접근 특성이 다르다. **대역폭**은 단위 시간에 옮길 수 있는 양, **지연시간**은 한 요청의 결과를 받기까지 걸리는 시간이다. 큰 파일을 순서대로 복사하는 성능과 작은 데이터를 반복해서 찾는 성능이 다른 이유다.

## 프로세스마다 메모리를 따로 보이게 한다

프로그램이 사용하는 **가상 주소**는 RAM의 실제 위치를 직접 가리키는 숫자가 아니다. 커널이 관리하는 주소 대응표를 통해 **물리 주소**로 연결된다. 이 **가상 메모리** 덕분에 프로세스마다 독립된 주소 공간을 제공하고, 같은 라이브러리 데이터를 공유하거나 당장 필요 없는 영역의 실제 배정을 늦출 수 있다. 가상 메모리는 단순히 “RAM이 부족할 때 쓰는 디스크”보다 넓은 개념이다.

주소 공간은 보통 **페이지(page)**라는 일정 크기 단위로 관리한다. **페이지 테이블**은 가상 페이지와 물리 메모리, 접근 권한 등의 대응을 담는다. CPU의 **MMU**가 이 변환과 권한 검사를 지원하고, **TLB**는 자주 쓰는 주소 변환을 캐시한다. 주소 변환을 매번 처음부터 찾는 비용을 줄이는 것이다. 프로그램에서 같은 주소를 사용해도 다른 프로세스의 페이지 테이블이 적용되면 다른 데이터를 가리킨다.

필요한 페이지를 바로 사용할 수 없거나 접근 조건을 만족하지 못하면 **페이지 폴트(page fault)**가 발생한다. 이것이 항상 프로그램 오류는 아니다. 처음 접근한 페이지에 메모리를 배정하거나 파일 내용을 읽어 오는 정상 처리일 수 있다. 접근 권한 위반처럼 처리할 수 없는 경우에는 프로그램에 오류가 전달된다. **요구 페이징(demand paging)**은 실제로 필요해졌을 때 페이지를 준비해 시작 시 모든 내용을 읽는 비용을 줄이는 방식이다.

**Copy-on-write(COW)**는 처음에는 같은 내용을 공유하다가 한쪽이 수정하려 할 때 그 부분을 따로 만드는 방식이다. 프로세스를 복제할 때 모든 메모리를 즉시 복사하지 않고도 독립된 변경 결과를 제공할 수 있다. 파일시스템·가상 디스크에서도 같은 아이디어를 사용하지만 구현과 보존 단위는 다르다.

## 캐시와 swap은 왜 필요한가

**CPU 캐시**는 CPU 가까이에 자주 쓰는 데이터를 보관해 RAM 접근 비용을 줄인다. **페이지 캐시(page cache)**는 커널이 파일 내용을 RAM에 보관해 같은 디스크 데이터를 반복해서 읽는 비용을 줄인다. 같은 “캐시”여도 위치와 관리 주체가 다르다. 캐시는 기존 데이터를 더 빠르게 다시 얻기 위한 사본이고, 아직 저장장치에 반영되지 않은 수정 내용은 특별히 관리해야 한다.

**버퍼(buffer)**는 데이터를 생산하는 쪽과 소비하는 쪽의 속도·크기 차이를 흡수하는 임시 저장 공간이다. 파이프 버퍼가 차면 생산자가 기다릴 수 있고, 쓰기 버퍼에 모인 데이터는 나중에 디스크로 전달될 수 있다. 커널은 수정됐지만 아직 저장장치에 반영하지 않은 **dirty page**를 추적하고 **writeback**으로 내려 보낸다. 앱이 요청한 저장의 지속성은 앱의 동기화 요청, 파일시스템, 장치의 처리까지 함께 관련된다.

**swap**은 RAM에서 당장 유지할 필요가 적은 익명 메모리 페이지 등을 저장장치로 옮길 공간이다. 익명 메모리는 보통 프로그램의 작업 데이터처럼 원래 파일에서 다시 읽을 수 없는 영역이다. 깨끗한 파일 캐시를 버렸다가 다시 읽는 것과 swap에 내용을 저장하는 것은 다른 처리다. swap은 RAM 압박을 완화할 수 있지만 RAM과 같은 속도의 확장 메모리는 아니다. 지속적인 입출력 교환이 많아지면 작업이 느려질 수 있다.

**OOM(out of memory)**은 필요한 메모리를 확보하지 못하는 상황이다. 커널은 조건에 따라 프로세스를 종료해 메모리를 회수할 수 있다. **메모리 누수**는 프로그램이 더 이상 필요 없는 메모리를 계속 보유하는 문제다. 사용량 증가가 모두 누수인 것은 아니며 캐시, 실제 작업 증가, 자원 제한을 함께 봐야 한다. 프로세스의 가상 주소 공간 크기와 실제 RAM에 올라온 **RSS**도 다르다.

우리 VM은 swap LV를 별도로 두고 monitoring에서 메모리 사용량을 표시한다. `free`의 free는 완전히 비어 있는 쪽, available은 캐시 회수 등을 고려해 새 작업에 쓸 수 있다고 추정하는 양이다. free가 작아도 곧바로 메모리 고갈이라고 판단할 수 없는 이유다.
