# 저장장치·암호화·LVM

[개념 지도](../concepts.md) · 먼저 읽기: [파일과 마운트](06-files.md)

## 주소가 있는 저장 공간을 나눈다

**블록 장치**는 위치를 지정해 일정 단위의 데이터를 읽고 쓰는 저장 인터페이스다. 디스크 전체, 디스크의 일부, 소프트웨어가 만든 가상 저장 영역이 블록 장치로 보일 수 있다. **섹터(sector)**는 장치가 주소를 매기는 단위와 관련되고, 파일시스템의 블록은 파일시스템이 관리하는 단위다. 항상 같은 크기라고 가정하면 크기 계산이 틀어질 수 있다.

**파티션(partition)**은 디스크의 주소 공간 일부를 구획으로 나눈 것이다. 어느 위치부터 어느 길이까지인지와 유형을 기록하는 것이 **파티션 테이블**이다. 파티션을 만들었다고 파일 이름을 저장할 구조까지 생긴 것은 아니며, 파일시스템이나 암호화·LVM 같은 다음 계층을 그 안에 만든다.

**MBR**과 **GPT**는 파티션 정보를 기록하는 서로 다른 형식이다. GPT는 더 큰 주소 공간과 여러 파티션을 다루고 복제된 메타데이터와 검사값도 둔다. GPT 자체가 데이터 백업이나 디스크 암호화는 아니다. BIOS·UEFI는 부팅 펌웨어 방식이고 GPT·MBR은 디스크 구획 형식이므로 서로 다른 축이다. 우리 설계의 BIOS와 GPT 조합에서는 부트로더가 사용할 BIOS Boot 영역을 별도로 둔다.

**ext4**와 **XFS**는 Linux에서 쓰는 파일시스템이다. 둘 다 파일·디렉터리·메타데이터를 관리하지만 내부 구조와 운영 도구, 크기 변경의 제약이 다르다. ext4는 조건에 맞춰 확대하고 언마운트 상태에서 축소할 수 있다. 이 프로젝트가 참고하는 RHEL 10의 XFS 운영 범위에서는 확장은 지원하지만 축소는 지원하지 않는다. 이 프로젝트는 축소 가능성도 고려해 ext4를 선택했으며 배포판의 기본 파일시스템 선택을 무조건 따라간 것이 아니다.

**저널링(journaling)**은 여러 단계의 파일시스템 변경을 기록으로 관리해 중간에 전원이 끊겼을 때 구조를 일관된 상태로 복구하는 데 도움을 주는 방식이다. 디렉터리 항목과 할당 정보가 절반만 바뀌는 문제를 줄이는 것이다. 모든 앱 데이터가 항상 최근 상태로 저장됐다는 보장이나 삭제한 파일의 백업은 아니다. 파일시스템 저널과 사람이 보는 시스템 로그도 역할이 다르다.

## 암호화는 그 위 계층을 보지 못하게 한다

**dm-crypt**는 Linux에서 블록 장치의 읽기·쓰기 데이터를 암호화해 변환하는 계층이다. **LUKS**는 암호화 설정과 키 슬롯 등의 메타데이터를 저장하는 형식이다. 사용자 암호를 이용해 실제 데이터 암호화 키를 사용할 수 있게 하고, 암호화된 저장 영역을 열면 그 위에 평문 블록 장치처럼 접근할 수 있는 연결을 제공한다.

예를 들어 잠긴 LUKS 영역에는 ext4나 LVM을 바로 읽을 수 없는 암호화된 데이터가 있다. 암호를 입력해 열면 위 계층이 평문 구조를 읽고 작동한다. 잠겨 있을 때 디스크를 가져간 사람이 내용을 읽기 어렵게 하는 것과, 열린 상태에서 어느 사용자가 파일을 읽을 수 있는지는 다른 문제다. 후자는 파일 권한과 SELinux 같은 접근 제어가 맡는다.

**LUKS 헤더**는 데이터 해제에 필요한 암호화 메타데이터를 담는다. 헤더 백업은 그 정보 손상에 대비하지만 파일 데이터 자체를 복제하지 않는다. 암호를 기억해도 필요한 메타데이터가 손상되면 해제에 문제가 생길 수 있으므로 키와 헤더, 데이터 보관은 서로 연관된다. 헤더 복구는 아무 헤더를 덮어쓰는 것이 아니라 해당 장치의 정확한 정보로 되돌리는 일이다.

## LVM은 공간을 풀로 관리한다

파티션만으로 `/home`과 `/var/log`를 나누면 처음 정한 경계가 나중의 필요와 맞지 않을 수 있다. **LVM(Logical Volume Manager)**은 물리 저장 영역과 사용자가 쓸 논리 저장 영역 사이에 관리 계층을 둔다. 여러 저장 영역을 한 풀로 모으고, 그 풀에서 필요한 크기를 배정하므로 실제 디스크 배치와 파일시스템 단위의 용량 결정을 분리할 수 있다.

**PV(physical volume)**는 LVM이 관리하도록 준비한 블록 장치다. **VG(volume group)**는 하나 이상의 PV를 모은 공간 풀이다. **LV(logical volume)**는 그 풀에서 일정 공간을 배정받은 논리 블록 장치다. PV의 공간은 **extent**라는 단위로 관리되고 LV의 논리 영역과 연결된다. 사용자는 어느 디스크의 어느 연속 구간인지보다 어느 LV에 얼마를 배정할지 다루게 된다.

LV는 아직 파일을 정리하는 파일시스템이 아니다. LV를 만든 뒤 ext4 등을 만들고 특정 디렉터리에 마운트해야 파일 경로로 사용할 수 있다. 이 분리 덕분에 같은 VG에서 하나의 LV는 ext4, 다른 LV는 swap처럼 다른 용도로 쓸 수 있다. LV를 늘리면 블록 장치의 크기가 커진 것이고 그 안의 파일시스템도 새 공간을 사용하도록 확대해야 한다.

가상의 예로 VG에 10 GiB가 남아 있고 `/var/log`의 LV가 2 GiB라면, 로그 파일시스템이 볼 수 있는 크기는 여전히 2 GiB다. `vgs`는 아직 어느 LV에도 배정하지 않은 풀의 여유를 보고, `df`는 이미 주어진 파일시스템 안의 여유를 본다. 따라서 VG의 10 GiB와 df의 0 GiB는 모순이 아니다. 풀의 공간을 LV에 배정하고 파일시스템을 늘려야 연결된다.

우리 구성은 다음 순서다. 암호화 계층을 어디에 두었는지도 여기서 드러난다.

```text
VDI → 디스크 파티션 → LUKS 해제 장치 → PV → VG LVM
                                            ├─ LV root → ext4 → /
                                            ├─ LV home → ext4 → /home
                                            ├─ LV var_log → ext4 → /var/log
                                            └─ LV swap → swap 공간
```

## 더 큰 저장 설계와의 연결

**RAID**는 여러 디스크를 묶어 성능이나 장애 내성을 얻는 방식이다. **스트라이핑**은 데이터를 여러 디스크에 나눠 배치하고, **미러링**은 같은 데이터를 복제하며, **패리티**는 일부 손실을 계산으로 복원할 정보를 둔다. 어떤 구성은 한 디스크 장애를 견디지만 잘못 삭제한 파일은 다른 디스크에서도 즉시 같은 상태가 되므로 백업과 다르다.

**thin provisioning**은 논리적으로 약속한 용량을 실제 사용 시점에 배정하는 방식이다. 당장 쓰지 않는 공간을 효율적으로 공유하지만 풀의 실제 공간이 바닥나면 여러 사용자가 동시에 영향을 받을 수 있다. 일반 VG 미할당 여유를 남기는 현재 구성과 같은 의미가 아니다. **LVM 스냅샷**은 블록 변경을 추적해 특정 시점의 논리 상태를 보존한다. VirtualBox가 관리하는 VM 스냅샷과는 생성 주체·범위가 다르다.

**TRIM/discard**는 사용하지 않게 된 블록을 아래 저장 계층에 알려 재사용·공간 관리에 도움을 주는 기능이다. 게스트에서 파일을 삭제했다고 호스트의 동적 VDI 파일이 즉시 작아지는 것은 아니다. 파일시스템·가상 디스크·호스트 저장장치까지 여러 계층의 지원과 처리가 연결되어야 한다.
