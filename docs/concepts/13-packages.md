# 배포판·패키지·업데이트

[개념 지도](../concepts.md) · 먼저 읽기: [운영체제](01-os.md), [파일](06-files.md)

## 실행 파일을 배포하는 단위

**소스 코드**는 사람이 프로그램을 작성하는 형태이고, **컴파일러**는 이를 다른 실행 형태로 번역하는 도구다. **목적 파일(object file)**은 번역된 코드와 연결에 필요한 정보를 담는 중간 산출물이다. **링커**는 목적 파일과 라이브러리의 참조를 연결해 실행 파일이나 공유 라이브러리를 만든다. 컴파일이 성공해도 필요한 함수 정의를 연결하지 못하면 최종 프로그램은 만들어지지 않을 수 있다.

**바이너리**는 문맥에 따라 사람이 읽는 소스와 대비되는 기계적 데이터·실행 산출물을 말한다. 이미 빌드된 프로그램도 CPU 명령어 집합과 ABI가 맞아야 실행할 수 있다. **정적 링크**는 필요한 라이브러리 코드를 결과물에 포함하는 방식이고, **동적 링크**는 실행할 때 공유 라이브러리와 연결하는 방식이다. 동적 링크는 코드를 공유하고 라이브러리를 별도로 갱신하기 쉽지만 호환되는 라이브러리가 필요하다.

**패키지**는 프로그램·설정·메타데이터·설치 작업 등을 배포와 관리의 단위로 묶은 것이다. 파일을 다운로드하는 것에 더해 어떤 파일이 어느 패키지 소유인지, 무엇이 필요한지 추적하게 한다. Rocky 계열의 **RPM**과 Debian 계열의 **deb**는 서로 다른 패키지 형식이다. 패키지 파일 형식과 그 파일들을 찾아 설치하는 관리 도구는 구분해야 한다.

## 필요한 부품을 함께 고른다

**의존성**은 패키지가 동작하려면 필요한 다른 기능·패키지·버전 조건이다. 하나의 도구를 설치했는데 라이브러리 여러 개가 함께 설치되는 이유다. **저장소(repository)**는 패키지와 조회용 정보를 제공하는 배포 위치다. Git 저장소와 이름은 같지만 여기서는 OS 패키지를 찾는 공급원이다. **저장소 메타데이터**에는 패키지 이름·버전·의존 관계 등 검색과 선택에 필요한 정보가 담긴다.

**DNF**는 Rocky 등의 시스템에서 저장소를 조회하고 의존성을 해결해 RPM 설치·갱신을 조정한다. **APT**는 Debian 계열에서 비슷한 상위 역할을 하고, **dpkg**는 로컬 deb 설치 상태 등을 관리하는 하위 도구다. DNF와 rpm, APT와 dpkg의 역할 층을 구분하면 다운로드한 파일 하나를 설치하는 일과 배포판 저장소에서 필요한 전체 조합을 해결하는 일의 차이가 보인다.

**패키지 서명**은 신뢰한 키로 공급자의 패키지 여부와 무결성을 검증하는 데 쓰인다. HTTPS 다운로드와 패키지 서명은 서로 다른 계층의 검증이다. 신뢰할 키와 저장소를 잘못 추가하면 서명이 존재해도 원하지 않는 공급자를 신뢰할 수 있다. **미러**는 같은 저장소 내용을 여러 위치에서 제공해 접근성과 부하를 개선한다. 어느 미러인지보다 신뢰 설정과 메타데이터의 유효성이 핵심이다.

검증을 연결하는 방식은 생태계마다 다르다. RPM에서는 개별 RPM 파일의 서명을 검증할 수 있다. Debian의 일반적인 APT 저장소에서는 서명된 `InRelease` 또는 `Release`와 분리 서명을 검증하고, 거기에 기록된 해시로 패키지 목록을, 다시 목록의 해시로 내려받은 `.deb`를 확인한다. 즉 APT가 모든 `.deb` 안의 개별 서명을 검사한다고 이해하면 안 된다. 이 연결은 신뢰한 저장소가 배포한 내용인지 확인하며, 패키지 코드가 무해하다는 심사까지 대신하지 않는다.

**패키지 트랜잭션**은 설치·제거·갱신할 변경들의 한 묶음이다. 의존성 조건을 먼저 풀어 전체 변경 계획을 만드는 데 의미가 있다. 그러나 데이터베이스의 완전한 원자적 트랜잭션처럼 전원 장애와 설치 스크립트의 모든 부작용이 항상 되돌려지는 것은 아니다. 변경 기록이 있다고 전체 시스템의 과거 상태가 보존된 것도 아니다.

## 버전 번호보다 유지 관리 정책을 읽는다

**패치**는 프로그램의 문제나 기능을 바꾸는 변경이다. **백포트**는 새 버전에 포함된 수정을 오래 유지하는 버전 계열에 옮기는 작업이다. 기업용 배포판에서 겉으로 보이는 상위 버전 번호가 낮아도 보안 수정이 포함될 수 있는 이유다. 특정 취약점의 수정 여부는 숫자의 크기만 비교하지 말고 해당 배포판의 공지와 패키지 릴리스를 함께 확인해야 한다.

**업데이트**와 **업그레이드**는 도구마다 쓰임이 다르지만, 개별 패키지 갱신과 배포판의 큰 버전 전환은 운영 영향이 다르다. DNF의 명령 이름만 보고 “upgrade면 반드시 Rocky 10에서 다음 주요 버전으로 이동한다”고 해석하면 안 된다. **릴리스 저장소**와 지원 정책이 어떤 버전 조합을 제공하는지가 실제 변경 범위를 결정한다.

**설정 파일 병합**은 패키지가 제공한 새 기본값과 관리자가 수정한 기존 값을 어떻게 유지할지의 문제다. RPM에서는 파일의 패키징 정책과 변경 여부에 따라 `.rpmnew`나 `.rpmsave` 같은 파일이 남을 수 있다. 새 패키지를 설치했다고 기존 설정이 자동으로 새 권장값이 된 것은 아니며, 설정을 보존했다고 새 기능과의 호환성이 자동 검증된 것도 아니다.

**롤백**은 변경 전 상태로 되돌리는 작업이다. 패키지 버전을 낮추는 것과 프로그램이 이미 바꾼 데이터 형식을 되돌리는 일은 별개다. **재현 가능한 빌드**는 같은 소스·환경 조건에서 동일한 산출물을 얻어 빌드 결과를 비교할 수 있게 하는 성질이다. 이는 공급 과정의 검증을 돕지만 실행 중인 서버의 설정과 데이터까지 저절로 재현해 주지는 않는다.
