# 네트워크: 상대 컴퓨터에서 프로세스까지

[개념 지도](../concepts.md) · 먼저 읽기: [가상화](02-virtualization.md), [프로세스](03-process.md)

## 같은 선에 연결된 장치와 그 너머의 주소

**네트워크 인터페이스(NIC)**는 컴퓨터가 네트워크에 참여하는 통로다. 물리적인 랜 카드도 있고 VM이 보는 가상 장치도 있다. Rocky의 enp0s3는 인터페이스 이름이지 인터넷 주소가 아니다. 하나의 인터페이스에 여러 주소가 붙을 수 있고 장치가 존재해도 주소나 경로가 준비되지 않으면 원하는 상대와 통신할 수 없다.

**Ethernet**은 같은 링크에서 데이터를 주고받는 방식 중 하나다. 그 전송 단위인 **프레임**에는 링크 안의 출발지·목적지를 나타내는 **MAC 주소** 등이 담긴다. 반면 **IP 주소**는 네트워크들을 넘어 목적지를 찾기 위한 논리적 주소다. 택배를 지역 운송 구간마다 다른 차량에 싣는 것처럼, IP 통신은 중간 링크마다 다른 프레임에 실릴 수 있다. MAC과 IP는 같은 대상의 두 별명이라기보다 서로 다른 범위의 전달에 쓰이는 정보다.

**IPv4**는 32비트 주소를 사용하며 192.0.2.10 같은 표기로 읽는다. **IPv6**는 128비트 주소를 사용하며 2001:db8::10처럼 표기한다. 주소 길이 외에 이웃 탐색과 패킷 처리 등도 다르다. IPv4 통신이 된다고 IPv6 경로와 방화벽까지 확인한 것은 아니다. 여기의 두 주소는 설명용 문서 주소이며 실제 VM에서 확인한 값이 아니다.

**서브넷**은 주소 공간을 공통 접두부로 묶어 다루는 범위다. **CIDR 접두부** `/24`는 IPv4 주소의 앞 24비트를 네트워크 부분으로 다룬다는 표기다. 예를 들어 192.0.2.10/24와 192.0.2.20/24는 같은 접두부를 가진다. 주소가 비슷하게 보이는지보다 접두부 길이까지 함께 비교해야 같은 링크로 보낼지 판단할 수 있다.

**ARP**는 IPv4의 같은 링크에서 다음으로 전달할 IP 주소에 대응하는 MAC 주소를 알아내는 프로토콜이다. 먼 서버의 MAC을 인터넷 전체에서 찾는 절차가 아니다. IPv6는 ARP 대신 **Neighbor Discovery**로 이웃 탐색·라우터 발견 등의 일을 한다. IP 주소를 잘못 설정한 경우와 링크의 이웃을 찾지 못하는 경우는 이처럼 서로 다른 단계의 문제다.

## 다른 네트워크로 보내는 길

**라우팅**은 목적지 주소에 맞는 다음 전달 경로를 고르는 일이다. 커널의 **라우팅 테이블**에는 목적지 접두부, 다음 홉, 인터페이스 등의 정보가 있다. 더 구체적으로 일치하는 경로가 우선하는 것이 기본 원리다. 따라서 기본 경로가 존재해도 특정 목적지에 더 구체적인 잘못된 경로가 있으면 통신이 실패할 수 있다.

**게이트웨이**는 다른 네트워크로 가기 위해 전달을 맡기는 다음 홉이다. **기본 경로**는 더 구체적인 경로가 없을 때 사용하는 선택지다. 로컬 상대에게는 게이트웨이를 거치지 않을 수 있다. **루프백**은 자기 컴퓨터 안의 통신을 위한 인터페이스·주소 범위이며, 127.0.0.1이나 ::1이 대표적이다. 호스트의 127.0.0.1과 게스트의 127.0.0.1은 각각 자기 환경을 가리킨다.

**MTU**는 한 링크에서 운반할 수 있는 네트워크 계층 패킷 크기의 상한과 관련된다. 작은 메시지는 되는데 큰 전송만 멈추는 현상은 경로의 MTU 처리와 연결될 수 있다. **VLAN**은 물리적인 네트워크를 논리적인 링크 영역들로 나누는 기술이다. 같은 스위치에 연결된 장치라도 VLAN이 다르면 단순한 같은 링크의 이웃이 아닐 수 있다. 둘은 각각 전송 크기와 링크 구분이라는 다른 문제를 해결한다.

## 목적지 컴퓨터 안에서 누구에게 전달할까

**전송 계층**은 IP로 도착한 데이터를 응용 프로그램의 통신으로 이어 준다. **TCP**는 연결을 만들고 순서·재전송·흐름 제어 등을 제공하는 바이트 스트림 프로토콜이다. 메시지 하나를 보냈다고 받는 쪽의 읽기 한 번에 똑같은 경계로 도착하는 것은 아니다. SSH는 이 스트림 위에서 자신만의 메시지 구조를 처리한다.

**UDP**는 데이터그램 단위로 보내며 TCP 같은 연결 설정·순서 보장·재전송을 기본 제공하지 않는다. 필요한 신뢰성은 응용 프로그램이 설계할 수 있다. 따라서 UDP를 단순히 “항상 빠르지만 못 믿는 TCP”로 외우기보다 프로그램이 어떤 보장을 직접 맡는지 봐야 한다. DNS는 UDP와 TCP를 모두 이용할 수 있다.

**포트**는 TCP·UDP에서 통신의 끝점을 구분하는 번호다. 같은 4242라도 TCP와 UDP는 별개의 공간이다. **소켓**은 프로그램이 통신을 다루는 운영체제 인터페이스이며, IP 통신에서는 주소·포트·프로토콜과 연결된다. 서버가 **리스닝(listening)**한다는 것은 특정 주소·포트에서 연결 요청을 받을 준비가 되었다는 뜻이다. 방화벽에서 포트를 열어도 그 포트에 리스닝하는 프로그램이 생기지는 않는다.

TCP의 **핸드셰이크**는 양쪽이 연결 상태를 맞추는 시작 교환이다. 그 뒤 SSH가 자체 프로토콜로 서버 신원과 사용자 인증을 진행한다. 따라서 “TCP 연결됨”과 “로그인 성공”은 서로 다른 단계다. 0.0.0.0에 바인딩한 서비스는 IPv4의 모든 로컬 인터페이스 주소를 대상으로 받도록 요청한 것이고, 127.0.0.1에만 바인딩한 서비스는 로컬 접근으로 범위가 좁다.

## VirtualBox의 네트워크와 이름 찾기

**NAT**는 경계를 통과하는 패킷의 주소 등을 변환한다. VirtualBox 기본 NAT에서 게스트가 외부로 나갈 수 있어도 외부에서 게스트의 모든 서비스에 바로 연결할 수 있는 것은 아니다. **포트 포워딩**은 호스트 쪽으로 들어온 특정 통신을 게스트의 지정 주소·포트로 이어 주는 규칙이다. 현재 운영 문서의 호스트 127.42.42.42:4242 → 게스트 TCP 4242라는 연결은 호스트 규칙, 게스트 방화벽, sshd 리스닝이 모두 맞아야 한다.

**브리지 네트워킹**은 게스트 인터페이스를 호스트의 물리 네트워크에 참여시키는 방식이다. 게스트가 같은 네트워크의 별도 장치처럼 주소를 받아 운영될 수 있으므로 NAT 포트 전달과 접근 범위가 다르다. **호스트 전용 네트워크**는 호스트와 해당 VM 사이의 별도 연결을 제공한다. 세 방식은 성능 순위가 아니라 누구와 어떤 경계를 통해 통신할지의 선택이다.

**호스트명**은 컴퓨터를 사람이 다루기 쉽게 부르는 이름이다. **DNS**는 이름을 주소 등 여러 종류의 기록으로 해석하는 분산 시스템이다. 게스트의 호스트명을 jungblee42로 정해도 다른 컴퓨터의 DNS에 자동으로 그 이름이 등록되지는 않는다. **리졸버**는 응용 프로그램의 이름 조회를 수행하는 구성 요소다. 로컬 hosts 파일과 DNS 등 실제 조회 경로는 시스템 설정에 따라 달라진다.

**DHCP**는 주소·기본 경로·DNS 서버 등 네트워크 설정을 임대 방식으로 전달한다. NAT 환경에서 IP가 자동으로 생겼다면 이런 자동 구성의 결과일 수 있다. DHCP가 주소를 정하고 DNS가 이름을 찾는 역할은 다르다. 인터넷 이름이 안 풀리는 문제를 SSH 비밀번호 변경으로 해결할 수 없는 이유도 이 계층 분리에 있다.
