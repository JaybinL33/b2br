# 가상 머신과 컨테이너

[개념 지도](../concepts.md) · 먼저 읽기: [운영체제](01-os.md)

## 독립된 컴퓨터 환경을 제공한다

**가상 머신(VM)**은 실제 컴퓨터의 자원을 이용하면서 별도 컴퓨터처럼 보이는 실행 환경이다. VM을 실행하는 바깥쪽 컴퓨터·운영 환경을 **호스트**, VM 안에서 실행하는 운영체제를 **게스트**라고 한다. VirtualBox 같은 가상화 소프트웨어는 게스트에 가상 CPU, 메모리, 디스크, 네트워크 장치를 제공한다. 게스트 커널은 이 장치들을 자신의 컴퓨터에 연결된 장치처럼 사용한다.

호스트에서 `b2br.vdi`는 파일 하나지만 게스트에서는 운영체제를 설치할 디스크다. 게스트가 파일을 저장하면 게스트의 파일시스템과 가상 디스크 계층을 거쳐 호스트의 VDI 파일에도 변경이 생긴다. 따라서 게스트 내부의 빈 공간과 호스트의 빈 공간은 별도다. 가상 디스크의 최대 크기가 30 GiB라고 해서 호스트에서 30 GiB가 항상 즉시 할당되는 것도 아니다. 동적 할당 이미지는 사용에 따라 호스트 파일이 커질 수 있다.

**가상화**는 호스트 CPU가 지원하는 실행 기능을 활용하는 경우가 많고, **에뮬레이션**은 다른 종류의 CPU나 장치 동작을 소프트웨어로 흉내 낸다. 후자는 다른 아키텍처를 실행하는 범위를 넓히지만 비용이 커질 수 있다. 컨테이너는 또 다른 방식으로, 보통 호스트 커널을 공유하면서 프로세스와 자원 범위를 분리한다. 이번 과제의 VM처럼 독립된 게스트 커널을 부팅하는 구조와 다르다.

개념 근거: [Rocky Introduction to Linux](https://docs.rockylinux.org/books/admin_guide/01-presentation/), [VirtualBox First Steps](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/Introduction.html). 아래에서는 같은 실행 환경 문제를 하이퍼바이저와 컨테이너가 어떻게 다르게 푸는지 확장한다.

## 하이퍼바이저는 무엇을 중재하는가

**하이퍼바이저(hypervisor)**는 VM의 실행과 자원을 중재하는 가상화 계층이다. 게스트마다 CPU와 메모리를 가진 것처럼 보이게 하면서 실제 자원을 나누고 서로 간섭하지 않게 한다. **Type 1**은 하드웨어 위에서 직접 VM을 관리하는 구조, **Type 2**는 일반 호스트 운영체제 위에서 실행되는 구조를 설명하는 분류다. VirtualBox는 보통 Type 2로 설명한다. 실제 구현에는 커널 모듈·하드웨어 가상화·사용자 공간 장치 모델이 함께 있어 이 구분만으로 성능이나 보안을 모두 판단할 수는 없다.

**하드웨어 지원 가상화**는 CPU가 게스트 실행과 특권 작업의 경계를 지원하는 기능이다. 게스트의 모든 명령을 일일이 소프트웨어로 번역하는 부담을 줄인다. **전가상화**는 게스트가 일반 하드웨어 환경에서 동작하는 것처럼 실행시키는 방식이고, **반가상화(paravirtualization)**는 게스트가 가상화 환경을 알고 특별한 인터페이스·드라이버로 협력하는 방식이다. 한 VM에서도 CPU 실행은 하드웨어 지원을 쓰고 I/O는 반가상화 드라이버를 쓰는 식으로 결합될 수 있다.

**vCPU**는 VM에 제공되는 CPU 실행 단위다. vCPU 두 개를 설정했다고 호스트의 물리 코어 두 개가 그 VM에 영구 독점 배정되는 것은 아니다. 호스트의 다른 작업과 스케줄링을 나눌 수 있다. **오버커밋(overcommit)**은 제공한 가상 자원의 합을 물리 자원보다 크게 잡는 운영 방식이다. 항상 모든 VM이 자원을 최대로 쓰지 않는다는 점을 이용하지만 동시에 부하가 몰리면 대기와 메모리 압박이 커진다.

## 컨테이너는 프로세스의 환경을 나눈다

**컨테이너(container)**는 격리된 파일·네트워크·프로세스 보기와 자원 조건에서 실행되는 프로세스 집합이다. Linux의 **namespace**는 프로세스가 보는 PID 목록, 네트워크 장치, 마운트 등의 범위를 나눈다. **cgroup**은 프로세스들을 묶어 CPU·메모리 사용을 계측하고 제한한다. 앞은 “무엇이 보이는가”, 뒤는 “얼마나 쓸 수 있는가”와 연결된다. 두 기능만으로 완전한 보안이 자동 보장되는 것은 아니며 권한·파일 접근 정책도 함께 작동한다.

컨테이너는 대체로 별도 게스트 커널을 부팅하지 않고 자신을 실행하는 Linux 커널을 공유한다. 그래서 컨테이너 안의 Rocky 사용자 공간과 호스트의 배포판이 다를 수 있어도 커널은 컨테이너가 가져온 새 Rocky 커널이 아니다. **chroot**는 프로세스가 경로의 시작으로 보는 루트를 바꾸는 기능이다. 파일 경로만 바꾸는 chroot를 네트워크·프로세스·권한까지 관리하는 컨테이너 전체와 같게 보면 안 된다.

**Docker**는 컨테이너를 만들고 배포·실행하는 도구 생태계다. **Docker Engine**은 명령을 받는 API·데몬과 실행 관리 기능을 제공하며, **컨테이너 런타임**은 격리 조건을 만들고 실제 프로세스를 시작하는 일을 맡는다. Docker라는 이름과 Linux 커널의 컨테이너 기능은 동일한 층이 아니다. 다른 도구도 같은 계열의 커널 기능과 표준 이미지 형식을 사용할 수 있다.

**Docker Desktop**은 GUI와 개발용 통합 환경을 포함한다. macOS나 Windows에서 Linux 컨테이너를 실행할 때는 Linux 커널을 제공하는 VM 계층이 필요하다. 이때 컨테이너들이 공유하는 것은 macOS 커널이 아니라 그 Linux 환경의 커널이다. Linux용 Docker Desktop도 자체 VM을 사용하므로 Linux 호스트에 직접 설치한 Docker Engine과 구분한다. “VM과 컨테이너 중 하나만 쓴다”가 아니라 VM 안에 여러 컨테이너를 실행하는 조합이 흔하다.

## 이미지, 실행 상태, 데이터

**컨테이너 이미지**는 프로그램 실행에 필요한 파일과 기본 실행 설정을 배포하는 형태다. 실행 중인 프로세스 그 자체는 아니다. **레이어(layer)**는 이미지 파일 변경을 누적하는 단위다. 여러 이미지가 같은 기본 레이어를 공유할 수 있고, 컨테이너를 실행하면 일반적으로 이미지 위에 개별 쓰기 층이 생긴다. 같은 이미지에서 컨테이너 둘을 만들어도 실행 이후의 파일 변경과 프로세스 상태는 서로 다를 수 있다.

**Dockerfile**은 이미지를 만드는 단계와 기본 설정을 기술하는 파일이다. 소스 파일을 복사하고 패키지를 설치하는 빌드와, 만들어진 이미지를 실행하는 런타임은 다른 시점이다. **레지스트리(registry)**는 이미지를 저장·배포하는 서버다. 이미지 **태그(tag)**는 사람이 붙인 참조 이름으로 다른 내용으로 옮겨질 수 있고, **다이제스트(digest)**는 특정 내용의 해시 식별자다. 같은 태그를 나중에 받아도 같은 이미지라는 보장은 없다.

**볼륨(volume)**은 컨테이너의 일회성 쓰기 층과 분리해 데이터를 보관하는 방식이다. **bind mount**는 호스트의 특정 경로를 컨테이너 안에 연결한다. 데이터베이스 데이터를 이미지에만 넣는 것과 별도 볼륨에 보관하는 것은 삭제·재배포 때의 결과가 다르다. **Compose**는 여러 서비스의 이미지·네트워크·볼륨 관계를 함께 선언하는 도구다. 예를 들어 앱과 데이터베이스를 각각 실행하면서 연결 관계를 한 파일로 관리한다.

VM 스냅샷은 가상 머신의 디스크·설정 상태를 되돌리기 위한 지점이고, 컨테이너 이미지는 프로세스를 새로 시작할 파일·설정 묶음이다. 이미지를 가지고 있다는 것만으로 실행 중 데이터베이스의 데이터나 메모리 상태가 백업된 것은 아니다. 우리 Born2beRoot는 VM을 직접 운영하지만, 컨테이너를 더해도 저장·네트워크·권한이라는 기초 계층은 사라지지 않는다.
